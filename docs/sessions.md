# HMAC Sessions

## Overview

By default the tpm2 provider authenticates TPM operations using
**password sessions**: the caller's authorization value is sent in plaintext
inside the TPM command. This is secure on a bus that the TPM trusts (e.g. a
dedicated LPC or SPI bus), but it may expose the key's `userAuth` value on
shared or untrusted transports.

An **HMAC session** replaces the plaintext password with a
[HMAC](https://trustedcomputinggroup.org/wp-content/uploads/TSS_ESAPI_v1p0_r08_pub.pdf)
computed over the command parameters and session nonces. The TPM verifies the
HMAC rather than the raw password, so the `userAuth` value is never transmitted
in the clear. Sessions can optionally be:

* **Salted** — an ephemeral salt is encrypted to a TPM key's public key (the
  *tpmkey*). Only the entity that holds that TPM key can derive the session
  encryption key, which provides confidentiality of the authorization value even
  against a passive observer on the command bus.
* **Bound** — the session is associated with a specific TPM object (the *bind
  key*). The bind key's `authValue` is folded into the session key, providing
  additional authentication binding between the session and the object.

Sessions are **per-context**: a new HMAC session is started when an operation
context is initialized (sign, decrypt, derive, key generation), reused for the
lifetime of that context with `TPMA_SESSION_CONTINUESESSION`, and flushed when
the context is freed.

When no session parameters are configured the provider falls back to the
default password session (`ESYS_TR_PASSWORD`), which is the same behavior as
before this feature was added.


## Parameters

Two string parameters control the session:

| Parameter             | Description                                                                                               |
| --------------------- | --------------------------------------------------------------------------------------------------------- |
| `tpm2.session-tpmkey` | URI of the TPM key used to encrypt the session salt (salted session). If omitted the session is unsalted. |
| `tpm2.session-bind`   | URI of the TPM key the session is bound to (bound session). If omitted the session is unbound.            |

Both parameters accept the same URI formats as other TPM key references:

| URI prefix          | Meaning                                                                              |
| ------------------- | ------------------------------------------------------------------------------------ |
| `handle:0xNNNNNNNN` | Persistent or transient TPM handle (e.g. `handle:0x81010001`)                        |
| `object:FILE`       | Serialized ESYS_TR context written by `tpm2_evictcontrol -o FILE`                    |
| `FILE`              | TSS2 PEM private key file (e.g. a key generated by `openssl genpkey -provider tpm2`) |

Either or both parameters may be supplied; supplying neither is valid and
simply keeps the default password session.

The `authValue` for the bind key is provided through the environment variable
`TPM2OPENSSL_SESSION_BIND_AUTH`. This is analogous to `TPM2OPENSSL_PARENT_AUTH`
for parent keys.


## Configuring a Session

Session parameters can be supplied in three ways depending on which OpenSSL
command and operation context is used.

### 1. Property query string (`-propquery`)

Supported by: **signing** (RSA, ECDSA)

Session parameters can be embedded in the property query string passed to
`-propquery`. The tpm2 provider parses `tpm2.session-tpmkey` and
`tpm2.session-bind` from the query string when creating a new signature
context.

```
openssl pkeyutl -provider tpm2 -provider base \
    -propquery "provider=tpm2,tpm2.session-tpmkey=object:tpmkey.obj" \
    -sign -inkey testkey.priv -rawin -in testdata -digest sha256 -out testdata.sig
```

Multiple session parameters are comma-separated inside the same `-propquery`
value:
```
openssl pkeyutl -provider tpm2 \
    -propquery "provider=tpm2,tpm2.session-tpmkey=object:tpmkey.obj,tpm2.session-bind=handle:0x81000001" \
    -inkey "handle:0x81000001?pass" -passin pass:mysecret \
    -sign -rawin -in testdata -out testdata.sig
```

### 2. Key/algorithm options (`-pkeyopt`)

Supported by: **signing**, **decryption**, **key exchange (ECDH)**, **key
generation**

Session parameters can be passed as algorithm options. This is the only
method available for operations whose context does not accept a property query
(decrypt, derive, key generation).

The `-pkeyopt` syntax uses a colon as the key-value separator:
```
openssl pkeyutl -provider tpm2 -provider base \
    -inkey testkey.priv \
    -pkeyopt "tpm2.session-tpmkey:object:tpmkey.obj" \
    -decrypt -pkeyopt rsa_padding_mode:oaep -in testdata.crypt -out testdata
```

For key generation:
```
openssl genpkey -provider tpm2 -algorithm RSA -pkeyopt bits:2048 \
    -pkeyopt "tpm2.session-tpmkey:object:tpmkey.obj" \
    -out testkey.priv
```

### 3. Environment variables

The bind key's `authValue` is always read from the environment, regardless of
how the session URIs were supplied:

| Variable                        | Description                                                                 |
| ------------------------------- | --------------------------------------------------------------------------- |
| `TPM2OPENSSL_SESSION_BIND_AUTH` | `authValue` of the bind key. If not set, an empty authorization is assumed. |


## Operations with Session Support

| Operation          | Context    | propq | pkeyopt |
| ------------------ | ---------- | ----- | ------- |
| RSA sign           | signature  | yes   | yes     |
| ECDSA sign         | signature  | yes   | yes     |
| RSA decrypt        | asymcipher | no    | yes     |
| ECDH key exchange  | keyexch    | no    | yes     |
| RSA key generation | keymgmt    | no    | yes     |
| EC key generation  | keymgmt    | no    | yes     |

Verification uses the public key only and does not require any authorization;
it always uses `ESYS_TR_NONE` for all session slots and is unaffected by
session configuration.


## Security Considerations

### Salt-encryption key must not be fetched over the bus

The `tpm2.session-tpmkey` parameter identifies the key whose public portion is
used to encrypt the session salt.  If that public key is obtained over the same
TPM command bus the session is meant to protect, an active man-in-the-middle
attacker can:

1. Intercept the `TPM2_ReadPublic` response and substitute their own public key.
2. Intercept `TPM2_StartAuthSession`, decrypt the salt (using their private
   key), re-encrypt it to the real TPM key, and forward the modified command.
3. Both the host and TPM derive session keys — but the attacker also knows the
   salt and can compute the same session key, defeating all session protection.

For this reason the provider **rejects `handle:` URIs** for `tpm2.session-tpmkey`.
Only URI formats that carry the public key from a trusted local source are
accepted:

| URI format                    | Public key source            | Accepted for tpmkey? |
| ----------------------------- | ---------------------------- | -------------------- |
| `handle:0x…`                  | `TPM2_ReadPublic` over bus   | **No** — rejected    |
| `object:FILE`                 | Deserialized from local file | Yes                  |
| `FILE` (PEM, `KEY_TYPE_BLOB`) | Embedded in PEM file         | Yes                  |

To produce an `object:` file from a persistent handle:
```
tpm2_readpublic -c 0x81010001 -o tpmkey.obj -f tpmt
```
Or serialize a persistent handle's ESYS_TR context:
```
tpm2_evictcontrol -c key.ctx -o tpmkey.obj 0x81010001
```

The `tpm2.session-bind` parameter is not subject to this restriction because
the bind key does not protect the confidentiality of the salt; it only ties the
session to a specific object.


## Using Operations Without a Session

No configuration change is needed to use the default password session. Simply
omit the `tpm2.session-tpmkey` and `tpm2.session-bind` parameters entirely.
The provider then passes `ESYS_TR_PASSWORD` as the authorization session, which
is the same behavior as in earlier versions of the provider.

```
# Sign without an HMAC session (password session, default behavior)
openssl pkeyutl -provider tpm2 -provider base \
    -sign -inkey testkey.priv -rawin -in testdata -digest sha256 -out testdata.sig
```

If you have previously set `TPM2OPENSSL_SESSION_BIND_AUTH` in the environment
for a session-enabled call, ensure it is unset or empty when you no longer want
session binding to take effect:

```
unset TPM2OPENSSL_SESSION_BIND_AUTH
openssl pkeyutl -provider tpm2 -provider base \
    -sign -inkey testkey.priv -rawin -in testdata -digest sha256 -out testdata.sig
```


## Examples

### Salted session (tpmkey only)

Use the Endorsement Key (EK) to encrypt the session salt. The session is
unbound, so no bind auth is required.

```bash
# Create EK and persist it
tpm2_createek -G rsa -c ek.ctx
EK_HANDLE=$(tpm2_evictcontrol -c ek.ctx | cut -d ' ' -f 2 | head -n 1)

# Generate a signing key
openssl genpkey -provider tpm2 -algorithm RSA -pkeyopt bits:2048 -out testkey.priv
openssl pkey -provider tpm2 -provider base -in testkey.priv -pubout -out testkey.pub

# Sign with a salted HMAC session
openssl pkeyutl \
    -provider tpm2 \
    -propquery "provider=tpm2,tpm2.session-tpmkey=handle:${EK_HANDLE}" \
    -provider base \
    -sign -inkey testkey.priv -rawin -in testdata -digest sha256 -out testdata.sig

# Verify
openssl pkeyutl -verify -pubin -inkey testkey.pub \
    -rawin -in testdata -digest sha256 -sigfile testdata.sig

tpm2_evictcontrol -c ${EK_HANDLE}
```

### Salted and bound session (tpmkey + bind)

Both the EK (for salt encryption) and the signing key itself (as the bind key)
are configured. The bind key's `authValue` must be provided via the environment
variable.

```bash
# Create EK and an AK with auth value "mysecret"
tpm2_createek -G rsa -c ek.ctx
EK_HANDLE=$(tpm2_evictcontrol -c ek.ctx | cut -d ' ' -f 2 | head -n 1)

tpm2_createak -C ek.ctx -G rsa -g sha256 -s rsassa -p mysecret -c ak.ctx
AK_HANDLE=$(tpm2_evictcontrol -c ak.ctx | cut -d ' ' -f 2 | head -n 1)

openssl pkey -provider tpm2 -propquery '?provider=tpm2' \
    -in "handle:${AK_HANDLE}" -pubout -out testkey.pub

# Sign with a salted and bound HMAC session
TPM2OPENSSL_SESSION_BIND_AUTH=mysecret \
openssl pkeyutl \
    -provider tpm2 \
    -propquery "provider=tpm2,tpm2.session-tpmkey=handle:${EK_HANDLE},tpm2.session-bind=handle:${AK_HANDLE}" \
    -inkey "handle:${AK_HANDLE}?pass" -passin pass:mysecret \
    -sign -rawin -in testdata -out testdata.sig

openssl pkeyutl -verify -pubin -inkey testkey.pub \
    -rawin -in testdata -sigfile testdata.sig

tpm2_evictcontrol -c ${AK_HANDLE}
tpm2_evictcontrol -c ${EK_HANDLE}
```

### Session tpmkey as serialized object

`tpm2_evictcontrol -o FILE` writes a serialized ESYS_TR context that can be
referenced with the `object:` URI prefix.

```bash
tpm2_createek -G rsa -c ek.ctx
EK_HANDLE=$(tpm2_evictcontrol -c ek.ctx -o ek.obj | cut -d ' ' -f 2 | head -n 1)

openssl pkeyutl \
    -provider tpm2 \
    -propquery "provider=tpm2,tpm2.session-tpmkey=object:ek.obj" \
    -provider base \
    -sign -inkey testkey.priv -rawin -in testdata -digest sha256 -out testdata.sig

tpm2_evictcontrol -c ${EK_HANDLE}
```

### Session tpmkey as TSS2 PEM file

Any RSA or EC key stored in TSS2 PEM format (generated by `openssl genpkey
-provider tpm2`) can serve as the tpmkey. The key is loaded transiently into
the TPM at session start and flushed when the context is freed.

```bash
# Generate an RSA key to use as the session tpmkey
openssl genpkey -provider tpm2 -algorithm RSA -pkeyopt bits:2048 -out session_key.pem

openssl pkeyutl \
    -provider tpm2 \
    -propquery "provider=tpm2,tpm2.session-tpmkey=session_key.pem" \
    -provider base \
    -sign -inkey testkey.priv -rawin -in testdata -digest sha256 -out testdata.sig
```

### RSA decrypt with session (`-pkeyopt`)

The asymcipher context (used for decrypt) does not support a property query, so
session parameters must be passed via `-pkeyopt`.

```bash
TPM2OPENSSL_SESSION_BIND_AUTH=mysecret \
openssl pkeyutl \
    -provider tpm2 -provider base \
    -inkey "handle:${DEC_HANDLE}?pass" -passin pass:mysecret \
    -pkeyopt "tpm2.session-tpmkey:handle:${EK_HANDLE}" \
    -pkeyopt "tpm2.session-bind:handle:${DEC_HANDLE}" \
    -decrypt -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 \
    -in testdata.crypt -out testdata
```

### ECDH key derivation with session (`-pkeyopt`)

The keyexch context also uses `-pkeyopt` for session parameters.

```bash
openssl pkeyutl \
    -provider tpm2 -provider base \
    -derive -inkey testkey.priv -peerkey peer.pub \
    -pkeyopt "tpm2.session-tpmkey:handle:${EK_HANDLE}" \
    -out secret.key
```

### Key generation with session

Session parameters for key generation are passed via `-pkeyopt`. This is useful
when generating a key under a parent that requires authorization: by binding the
session to the parent, the parent's `authValue` is protected in transit.

```bash
TPM2OPENSSL_SESSION_BIND_AUTH=parentpw \
openssl genpkey -provider tpm2 -propquery '?provider=tpm2' -algorithm RSA \
    -pkeyopt bits:2048 \
    -pkeyopt "parent:${PARENT_HANDLE}" \
    -pkeyopt parent-auth:parentpw \
    -pkeyopt "tpm2.session-tpmkey:handle:${EK_HANDLE}" \
    -pkeyopt "tpm2.session-bind:handle:${PARENT_HANDLE}" \
    -out testkey.priv
```
